== Concerns ==
1. Target spec era <500ms; resultado ~733ms warm. La razon es que la query
   de existencia (TINV_MOVIMIENTO bulk) ya gasta ~730ms — el um_join solo
   ahorraba ~20ms y ya estaba bien con plan PUSHED PREDICATE.
2. El verdadero hot spot post-G1 es la existencia. Posibles caminos
   (FUERA del scope G1):
   - Cache de existencia (TTL ~30s) por (no_cia, almacen, fecha).
   - Materialized view / snapshot table TINV_EXISTENCIA refrescada por
     trigger sobre TINV_MOVIMIENTO.
   - Lazy load: devolver items sin existencia y completarla por lote vía
     endpoint /api/inv/existencia-bulk/ del frontend.
3. El refactor G1 SI vale la pena: en search '%A%' o paginas profundas
   sobre datasets grandes, el um_join PUSHED PREDICATE podia degradarse
   bajo carga concurrente; ahora el SQL paginado es Cost 2 estable.

== Proximo paso recomendado ==
Crear ticket separado "G1.b — Cache/snapshot de existencia normalizada"
con spec propio, fuera del bloque G1 actual.
